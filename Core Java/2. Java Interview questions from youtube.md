#### 1. **Difference between @Controller and @RestController in Spring**
   - **Question**: Tell me the difference between `@Controller` and `@RestController` in Spring. What is the basic difference?
   - **Answer**:
     - Both `@Controller` and `@RestController` are used to mark classes that handle client requests (e.g., from browsers, Postman, or other applications) via a front controller.
     - **@Controller**:
       - A generalized annotation for handling requests.
       - Can return logical view names resolved by a view resolver to render web pages (e.g., JSP, Thymeleaf).
     - **@RestController**:
       - A specialized version of `@Controller`, combining `@Controller` and `@ResponseBody`.
       - Handles REST-based requests, returning data (e.g., JSON or XML) directly in the response body, not view names.
       - `@ResponseBody` ensures the return value is serialized (e.g., as JSON for REST endpoints or as a string for web-based requests).
     - Example: `@RestController` is used for REST APIs returning JSON, while `@Controller` might return a view name for rendering a webpage.

#### 2. **How a Spring Boot Application Bootstraps**
   - **Question**: Tell me how a Spring Boot application bootstraps. When you run a Spring Boot application, what happens for a web-based application, a standalone application, or a reactive application?
   - **Answer**:
     - A Spring Boot application starts with a main class annotated with `@SpringBootApplication`, which combines three annotations:
       1. `@ComponentScan`: Scans for components, services, and controllers in the specified package.
       2. `@EnableAutoConfiguration`: Enables auto-configuration of dependencies based on the classpath.
       3. `@Configuration`: Marks the class as a source of bean definitions.
     - Spring Boot is opinionated, auto-configuring dependencies (e.g., via `@ConditionalOnBean`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty`, `@ConditionalOnClass`) to quickly set up the application.
     - Depending on the dependencies in the classpath:
       - **Standalone Application**: Uses a basic `ApplicationContext` (e.g., `AnnotationConfigApplicationContext`) to manage beans.
       - **Web-based Application**: Creates a `WebApplicationContext` to handle web-related beans (e.g., controllers, handler mappings).
       - **Reactive Application**: Creates a reactive container for reactive streams.
     - The container (context) holds all beans (e.g., controllers, services) and is configured automatically based on the application type.

#### 3. **Best Practices for Building REST APIs**
   - **Question**: What are the best practices you should follow when building REST APIs? If given a task to create a REST API, what standards will you follow, and why?
   - **Answer**:
     - **Purpose**: REST APIs should be usable by developers and non-developers within or outside the organization, requiring a common standard for usability.
     - **Best Practices**:
       1. **Versioning**:
          - Essential to manage API evolution (major updates, minor updates, patches).
          - Prevents breaking changes for clients by maintaining multiple versions (e.g., `/v4` and `/v5` in URLs).
          - Example: If a client requests additional properties in the JSON payload, changing the existing API without versioning could break their code. Versioning ensures backward compatibility.
       2. **Documentation**:
          - Comprehensive documentation for each API version, covering:
            - URLs, methods, response codes, request/response bodies, headers.
            - Examples of expected inputs and outputs.
          - Ensures clients know exactly what to send and expect.
       3. **Response Codes**:
          - Follow HTTP status code standards:
            - 200 series: Success (e.g., 200 OK).
            - 300 series: Redirection (e.g., 302 Found).
            - 400 series: Client-side errors (e.g., 400 Bad Request).
            - 500 series: Server-side errors (e.g., 500 Internal Server Error).
          - Avoid misusing codes (e.g., using 302 for success).
       4. **Content Type**:
          - Specify expected content types (e.g., JSON, XML) in requests and responses.
          - Document flexibility (e.g., accepting multiple content types).
       5. **Error Handling**:
          - Provide meaningful error responses to help clients debug issues.
          - Include details about what went wrong (e.g., missing fields, invalid data).
       6. **Statelessness**:
          - REST APIs should be stateless, meaning no server-side state is stored between requests.
          - Avoid storing user state (e.g., via cookies) on the server, as it’s problematic in distributed systems like microservices where requests may go to different instances.
          - Use token-based authentication (e.g., JWT) instead of cookies or sessions for statelessness.
       7. **Security**:
          - Document security requirements (e.g., basic authentication, token-based, JWT).
          - Enable SSL to secure data in transit and prevent hacking.
       8. **Pagination**:
          - For endpoints returning large datasets (e.g., `/books` with thousands of records), use pagination to return data in chunks (e.g., 10 or 100 records per page).
          - Improves performance and user experience by avoiding large data transfers.
     - **Reasoning**: These practices ensure APIs are maintainable, scalable, and user-friendly, preventing issues like breaking client applications or performance bottlenecks.

#### 5. **Differences Between Monolithic and Microservices Architectures**
   - **Question**: What are the basic differences between a monolithic application and a microservices-based architecture? Are monolithic applications bad? Should we avoid them entirely, or should new applications be microservices-based? Provide a solid comparison.
   - **Answer**:
     - **Monolithic Architecture**:
       - All modules are packaged into a single JAR or WAR file.
       - Modules interact via access modifiers (e.g., public, private, protected) within the same project.
       - **Challenges**:
         - Deployment: Entire JAR/WAR must be redeployed for any change, making the CI/CD pipeline slow and complex.
         - Scalability: Scaling requires replicating the entire application, even if only one module needs scaling (e.g., scorecard module during IPL season).
         - Testing: Changes in one module can break others due to tight coupling, requiring extensive testing.
         - Performance: Inter-module communication is fast (within the same JVM), but large deployments become bulky.
       - **Advantages**:
         - Simpler for small projects or startups with limited resources.
         - Faster inter-module communication since it’s within the same process.
     - **Microservices Architecture**:
       - Each module is a separate project (service) deployed independently.
       - Services communicate via REST APIs, Feign clients, or RestTemplates.
       - **Advantages**:
         - Scalability: Scale only the required service (e.g., scorecard service during IPL season) without scaling unrelated services.
         - Testing: Services are self-sufficient, reducing the risk of one service’s changes breaking others.
         - Deployment: Independent deployments allow faster updates and CI/CD pipelines.
       - **Challenges**:
         - Complexity: Managing multiple services, network calls, and configurations (e.g., API gateways, load balancers).
         - Performance: Inter-service communication involves network calls, which are slower than in-process calls in monolithic apps.
     - **Comparison and Decision**:
       - **Monolithic**: Suitable for small projects, pilot projects, or startups with limited resources. Easier to develop initially but harder to scale or maintain as the project grows.
       - **Microservices**: Ideal for large, complex systems requiring scalability and independent deployments but introduces complexity (e.g., service discovery, network latency).
       - Decision depends on requirements: Start with monolithic for simplicity and migrate to microservices if needed, ensuring the initial design supports future migration.
     - **Conclusion**: Neither is inherently bad; the choice depends on project size, complexity, and resources. Monolithic is simpler for startups, while microservices suit scalable, distributed systems.

#### 6. **Service Discovery in Microservices**
   - **Question**: In a microservices environment with multiple instances (e.g., five instances of a service), how do you discover and track these instances? What pattern is used for inter-service discovery?
   - **Answer**:
     - **Pattern**: Service Registration and Discovery.
     - **Process**:
       - Each microservice registers itself with a **service registry** (e.g., Eureka) upon startup, providing details like service name, hostname, port, and endpoints.
       - The registry acts as a repository storing information about all running instances.
       - Services fetch (discover) instance details from the registry using the service name, caching them locally.
       - Client-side load balancing can be applied to select an instance (e.g., using round-robin or other algorithms).
     - **Benefits**:
       - Avoids hardcoding URLs or ports, as instances can scale up/down dynamically.
       - Enables dynamic discovery of available instances.
     - **Handling Failures**:
       - If an instance crashes, the registry updates its records (e.g., every 30 seconds via a background thread).
       - If a service attempts to call a crashed instance, the client-side cache refreshes from the registry, selecting a live instance to avoid immediate exceptions.

#### 7. **Handling a Crashed Microservice Instance**
   - **Question**: If a service (e.g., Service A) tries to call an instance of another service (e.g., Service B) that has crashed, but the local cache still lists it, what happens? Will the call fail, and how is this handled?
   - **Answer**:
     - If Service A calls a crashed instance of Service B (listed in its local cache), the call may initially fail, resulting in an exception.
     - **Mitigation**:
       - A background thread refreshes the local cache periodically (e.g., every 30 seconds) from the service registry (e.g., Eureka).
       - If the crashed instance is removed from the registry, the updated cache will exclude it, and Service A will select a live instance.
       - Libraries like Eureka or Consul handle this by refreshing the cache and retrying calls to other instances, avoiding immediate exceptions.
       - If multiple attempts fail, a fallback response may be returned to prevent cascading failures.

#### 8. **Client-Side vs. Server-Side Load Balancing**
   - **Question**: How does Service A choose which instance of Service B to call when there are multiple instances? What is client-side load balancing, and how does it differ from server-side load balancing?
   - **Answer**:
     - **Load Balancing Concept**: Distributes incoming requests across multiple instances to balance load and improve performance.
     - **Client-Side Load Balancing**:
       - The calling service (e.g., Service A) uses its local cache (from the service registry) to select an instance of Service B.
       - Algorithms like round-robin or random selection are applied locally to choose an instance.
       - Reduces network calls, as no intermediate server is involved.
       - Libraries: Spring Cloud Load Balancer, Ribbon (outdated).
     - **Server-Side Load Balancing**:
       - A dedicated server (e.g., API gateway or load balancer) routes requests to Service B instances based on load or algorithms (e.g., round-robin).
       - Adds an extra network hop, increasing latency.
       - Risk: Single point of failure if the load balancer fails, though mitigated by scaling load balancers (e.g., multiple gateways).
     - **Key Difference**:
       - Client-side: The calling service handles load balancing, reducing network calls and avoiding a single point of failure.
       - Server-side: A dedicated server handles routing, which may introduce latency and a potential failure point.
     - **Tools**: Spring Cloud Load Balancer for client-side; Spring Cloud Gateway can perform server-side load balancing.

#### 9. **Handling Failures in a Microservices Chain**
   - **Question**: In a micro-services chain (e.g., Service A → B → C → D → E), if one service fails, the entire chain may break, returning an error to the client. How do you handle such failures to ensure the system remains resilient?
   - **Answer**:
     - **Problem**: A failure in one service (e.g., Service D) can cascade, causing the entire chain to fail and return an error to the client.
     - **Solutions**:
       1. **Resilience4j Library**: Used in Spring to make microservices resilient.
       2. **Fallback Response**:
          - Each service should return a default or fallback response if it cannot connect to a dependent service or if the dependent service fails.
          - Prevents cascading failures by providing a graceful response.
       3. **Circuit Breaker Pattern**:
          - Monitors calls to a service and “opens” the circuit if failures exceed a threshold (e.g., 10 failed requests).
          - In the “open” state, no further calls are made to the faulty service, giving it time to recover.
          - After a configured time (e.g., 10 seconds), the circuit moves to a “half-open” state, allowing a limited number of test calls to check if the service has recovered.
          - If successful, the circuit closes, resuming normal calls; if not, it reopens.
       4. **Retry Pattern**:
          - Retries a failed request a few times (e.g., due to network issues or temporary unavailability) before returning a fallback response.
          - Improves chances of success without immediately failing.
       5. **Rate Limiter**:
          - Limits the number of requests per time period (e.g., 100 requests per 10 seconds) to prevent overloading a service.
          - Protects against denial-of-service (DoS) attacks or excessive load.
       6. **Bulkhead Pattern**:
          - Isolates services by allocating separate thread pools, preventing a slow service from consuming all resources and affecting others.
     - **Goal**: Ensure fault tolerance by gracefully handling failures, returning fallback responses, and preventing system-wide crashes.

#### 10. **Circuit Breaker vs. Rate Limiter**
   - **Question**: How are circuit breaker and rate limiter patterns different? In which scenarios are they used?
   - **Answer**:
     - **Circuit Breaker**:
       - Breaks the connection to a faulty service if failures exceed a threshold, preventing further calls.
       - States: Closed (allows calls), Open (blocks calls), Half-Open (tests recovery with limited calls).
       - Use Case: When a service is down or unresponsive, to avoid overloading it and allow recovery time.
     - **Rate Limiter**:
       - Limits the number of requests a service accepts in a time period (e.g., 100 requests per 10 seconds).
       - Does not break the circuit but rejects excess requests to prevent overload.
       - Use Case: Protects against DoS attacks or excessive load from malicious or misconfigured clients.
     - **Key Difference**:
       - Circuit breaker stops calls to a faulty service; rate limiter controls the rate of incoming requests to a healthy service.
       - Both contribute to fault tolerance but address different scenarios.

#### 13. **Entity Object vs. Value Object in Hibernate**
   - **Question**: What is the major difference between an entity object and a value object in Hibernate? In which scenarios are they used?
   - **Answer**:
     - **Entity Object**:
       - Annotated with `@Entity`, representing a table in the database.
       - Has a unique identifier (e.g., `@Id` for primary key).
       - Used when data needs to be persisted independently in a separate table.
       - Example: A `Student` entity with `id`, `name`, `bloodGroup` maps to a `students` table.
     - **Value Object**:
       - Not annotated with `@Entity`, does not have a dedicated table.
       - Embedded within an entity using `@Embedded` and `@Embeddable`.
       - No unique identifier; its lifecycle is tied to the owning entity.
       - Example: An `Address` object (with `lane`, `city`, `zipCode`) embedded in a `Student` entity, stored in the `students` table as columns.
     - **Differences**:
       - **Identity**: Entities have a unique ID; value objects do not.
       - **Persistence**: Entities are stored in separate tables; value objects are stored as part of an entity’s table.
       - **Lifecycle**: If the owning entity (e.g., `Student`) is deleted, the value object (e.g., `Address`) is also deleted. Entities can exist independently.
     - **Scenarios**:
       - **Entity**: Use for objects needing independent persistence (e.g., `Address` for a property dealer needing to retain addresses even if a student is deleted).
       - **Value Object**: Use for objects that are attributes of another entity and do not need separate persistence (e.g., `Address` in a course management system, deleted when the student is deleted).
     - **Example**:
       - Course Management: `Student` (entity) with embedded `Address` (value object) in one table.
       - Property Dealer: `Student` and `Address` as separate entities with foreign key relationships, stored in separate tables.

#### 14. **Setting Up One-to-One Mapping in Hibernate**
   - **Question**: What is one-to-one mapping in Hibernate/Spring Boot? How do you set it up, and what are the major considerations?
   - **Answer**:
     - **Definition**:
       - One-to-one mapping defines a relationship where one instance of an entity (e.g., `Student`) is associated with exactly one instance of another entity (e.g., `Address`), and vice versa.
       - Example: One student has one address, and one address belongs to one student.
     - **Setup in Hibernate**:
       - Use `@OneToOne` annotation to define the relationship.
       - Use `@JoinColumn` to specify the foreign key column in one of the tables.
       - Example:
         ```java
         @Entity
         public class Student {
             @Id
             private Long id;
             private String name;
             @OneToOne
             @JoinColumn(name = "address_id")
	             private Address address;
         }

         @Entity
         public class Address {
             @Id
             private Long id;
             private String lane;
             private String city;
             private String zipCode;
         }
         ```
       - The `address_id` column in the `students` table references the `id` of the `addresses` table.
     - **Bidirectional Mapping**:
       - Define the relationship on both sides (e.g., `Address` also references `Student`).
       - Use `mappedBy` to avoid duplicate foreign keys:
         ```java
         @Entity
         public class Address {
             @Id
             private Long id;
             private String lane;
             private String city;
             private String zipCode;
             @OneToOne(mappedBy = "address")
             private Student student;
         }
         ```
     - **Cascading**:
       - Use `cascade` to propagate operations (e.g., save, delete) from one entity to the other.
       - Example: `cascade = CascadeType.ALL` ensures deleting a `Student` also deletes its `Address`.
       - `CascadeType.REFRESH`: Refreshes the child entity (e.g., `Address`) when the parent (e.g., `Student`) is refreshed, ensuring cache consistency.
     - **Considerations**:
       - Decide the owning side (where the foreign key resides, typically the side with `@JoinColumn`).
       - Choose unidirectional (one side references the other) or bidirectional (both sides reference each other) based on requirements.
       - Use cascading selectively to control which operations propagate (e.g., avoid cascading deletes if `Address` should persist independently).
       - Ensure proper indexing and constraints for performance and data integrity.

#### 15. **Exchange in Message Brokers**
   - **Question**: What is an exchange in a message broker like RabbitMQ, Kafka, or ActiveMQ? Why do we need it?
   - **Answer**:
     - **Message Broker Concept**:
       - Message brokers (e.g., RabbitMQ, ActiveMQ, Kafka) implement a producer-consumer model.
       - Producers send messages to a queue, and consumers retrieve them (e.g., in a FIFO manner).
     - **Exchange**:
       - An exchange is a component in message brokers (e.g., RabbitMQ) that receives messages from producers and routes them to one or more queues based on routing rules.
       - Queues are bound to exchanges, and exchanges determine how messages are distributed to queues.
     - **Purpose**:
       - Acts as a message broadcaster, allowing flexible routing to multiple queues.
       - Supports patterns like direct, topic, fanout, or headers-based routing in RabbitMQ.
       - Enables decoupling of producers and consumers, allowing messages to be processed asynchronously.
     - **Example**:
       - In RabbitMQ, a producer sends a message to an exchange, which routes it to a queue based on a routing key. Consumers subscribed to the queue process the message.
     - **Why Needed**:
       - Provides flexibility in message routing, allowing multiple consumers to process messages based on specific criteria.
       - Supports microservices patterns where services communicate asynchronously via messages.

#### 1. **What are SOLID Principles, Why Are They Needed, and Explain Single Responsibility Principle (SRP)?**
   - **Question**: Tell me about the SOLID principles. What do you mean by SOLID, why do we need it in real-time programming or daily jobs, and explain the Single Responsibility Principle.
   - **Answer**:
     - **SOLID Overview**:
       - SOLID principles are design guidelines to make code cleaner, more structured, and less dependent, ensuring changes in one part don’t affect others.
       - Comprises five principles:
         1. **S**ingle Responsibility Principle (SRP).
         2. **O**pen/Closed Principle (open for extension, closed for modification).
         3. **L**iskov Substitution Principle.
         4. **I**nterface Segregation Principle.
         5. **D**ependency Inversion Principle.
     - **Why Needed**:
       - Enhances code maintainability and scalability.
       - Reduces coupling, minimizing bugs during modifications.
     - **Single Responsibility Principle (SRP)**:
       - States: A class should have **only one responsibility** and thus only one reason to change.
       - Example: A persistence layer class should only handle database operations; a service layer class should only manage business logic.
       - **Benefit**: Limiting a class to one responsibility reduces the likelihood of changes impacting unrelated parts, lowering bug risks.

#### 2. **How to Define Responsibility and Assess SRP Compliance in a Class?**
   - **Question**: How do you define the term "responsibility"? If you’re reviewing a class with lots of code, how do you determine if it follows SRP? What parameters do you consider to check if a class violates SRP?
   - **Answer**:
     - **Defining Responsibility**:
       - Responsibility refers to a single, specific task or role a class performs (e.g., database operations, business logic).
     - **Assessing SRP Compliance**:
       - A class violates SRP if it handles multiple responsibilities, leading to multiple reasons for change.
       - **Example**:
         - A `Vehicle` class handling driving, maintenance, and insurance claims violates SRP.
         - Driving should be in a `Vehicle` class, maintenance in a `MaintenanceService` class, and insurance in an `InsurancePolicy` class.
       - **Parameter for Evaluation**:
         - Count the reasons a class might change. If there’s only one reason (e.g., updating driving logic), it follows SRP. Multiple reasons (e.g., updating driving, maintenance, and insurance) indicate a violation.

#### 5. **Where Are New String Objects Stored, and How Does Java Prevent Heap Memory Issues?**
   - **Question**: If strings are immutable and modifying a string creates a new object, where is the new object stored (Heap, String Constant Pool, or Stack)? If many string objects are created, won’t the Heap run out of memory, slowing the application due to garbage collection? How does Java address this?
   - **Answer**:
     - **Storage**:
       - String literals (e.g., `String s = "hello"`) are stored in the **String Constant Pool (SCP)**, a special area within the Heap memory.
       - Strings created with the `new` keyword (e.g., `String s = new String("hello")`) create an object in the Heap (outside SCP) and may reference the SCP for the literal.
     - **Preventing Heap Issues**:
       - The SCP optimizes memory by reusing string literals. If a literal (e.g., `"Abhilash"`) is already in the SCP, new references point to the existing object instead of creating duplicates.
       - Example: Five variables assigned `"Abhilash"` share one SCP object, reducing memory usage.
       - Immutable strings ensure safe sharing in the SCP, as their values cannot change.
     - **Garbage Collection**:
       - Unused string objects in the Heap are eligible for garbage collection, preventing memory exhaustion.
       - The SCP’s reuse mechanism minimizes object creation, reducing garbage collection overhead.

#### 6. **How Many String Objects Are Created in a Code Snapshot?**
   - **Question**: Given a code snapshot (e.g., `String s1 = "hello"; String s2 = new String("hello"); String s3 = "hello"; String s4 = new String("hello");`), how many objects are created, and where are they stored?
   - **Answer**:
     - **Analysis**:
       - `s1 = "hello"`: Creates one object in the SCP (within Heap).
       - `s2 = new String("hello")`: Creates one object in the Heap (outside SCP). The `"hello"` literal is already in the SCP (from `s1`), so no new SCP object is created.
       - `s3 = "hello"`: No new object; `s3` references the existing `"hello"` in the SCP.
       - `s4 = new String("hello")`: Creates another object in the Heap (outside SCP). The `"hello"` literal remains in the SCP.
     - **Total Objects**: Three objects:
       - One in the SCP (`"hello"`).
       - Two in the Heap (`s2` and `s4` instances).
     - **Reasoning**:
       - Literals reuse SCP objects to avoid duplicates.
       - The `new` keyword forces new Heap objects, even if the literal exists in the SCP.

     - **Analysis**:

       - `number = 100`: Creates an `Integer` object.
       - `s2 = number.toString()`: Creates a new `String` object in the Heap (not SCP) with value `"100"`.
       - `s1 == s2`: **False**, because `==` compares object references. `s1` points to the SCP object, while `s2` points to a new Heap object.
       - `s1.equals(s2)`: **True**, because `equals` compares string values, and both are `"100"`.
     - **Making `s2` Point to SCP**:
       - To make `s2` reference the SCP’s `"100"`, use `s2.intern()`. The `intern()` method checks if `"100"` exists in the SCP and returns its reference, making `s1 == s2` true.
       - Alternatively, assign `s2 = "100"` directly to use the SCP literal.

#### 8. **HashMap Fetch Time Across Buckets**
   - **Question**: In a HashMap with 10,000 buckets, if one element is in the 7th bucket and another in the 9,999th bucket, will the fetch time differ? How does HashMap ensure consistent fetch time?
   - **Answer**:
     - **Fetch Time**: Equal for both buckets (constant time, O(1) on average).
     - **Reason**:
       - HashMap uses an array of buckets, indexed by a hash code derived from the key.
       - The hash code is computed using the key’s `hashCode()` method, modulo the array size (`n-1`), to determine the bucket index.
       - Array access is constant time, regardless of the index (7th or 9,999th).
       - If collisions occur (multiple keys in the same bucket), a linked list or red-black tree (Java 8+) is used, but the initial bucket access remains O(1).
     - **Key Requirements**:
       - Keys must override `hashCode()` and `equals()` to ensure correct bucket placement and collision resolution.
       - During fetch, the key’s hash code locates the bucket, and `equals()` compares keys within the bucket.

#### 9. **HashMap Resizing and Index Recalculation**
   - **Question**: If a HashMap with an initial capacity of 16 reaches 75% capacity (12 elements, load factor 0.75), it doubles to 32 buckets. Are existing elements’ hash codes and indices recalculated, or do new elements just use the new size?
   - **Answer**:
     - **Recalculation Required**:
       - When the HashMap resizes (doubles from 16 to 32 buckets), all existing elements’ indices are recalculated.
       - The hash code of a key remains unchanged (as `hashCode()` is fixed).
       - The index is calculated as `hashCode % (n-1)`, where `n` is the array size. When `n` changes from 16 to 32, the modulo result changes, requiring rehashing of all elements to new buckets.
     - **Reason**:
       - Resizing redistributes elements to maintain load balance and prevent performance degradation.
       - Without recalculation, elements would remain in old indices, leading to uneven distribution in the larger array.

#### 10. **Can HashMap Accept Null Keys?**

#### 11. **Why Doesn’t Java Allow Multiple Inheritance with Classes but Allows It with Interfaces?**
   - **Question**: Java doesn’t support multiple inheritance with classes but allows it with interfaces. Why? Explain with the diamond problem.
   - **Answer**:
     - **Reason**: The **diamond problem** causes ambiguity in multiple inheritance with classes.
     - **Diamond Problem Example**:
       - A base class `Car` has a `drive()` method.
       - Two subclasses, `PetrolCar` and `ElectricCar`, inherit from `Car` and override `drive()`.
       - If a `HybridCar` class could inherit from both `PetrolCar` and `ElectricCar` (multiple inheritance), it would inherit two `drive()` methods with the same signature, creating ambiguity about which to use.

       - **Classes**: Contain method implementations, so multiple inheritance leads to conflicts (e.g., which `drive()` to call?).
       - **Interfaces**: Historically had only abstract methods (pre-Java 8) or default methods (Java 8+). Conflicts are resolved by requiring the implementing class to override ambiguous methods or explicitly select a default implementation.
     - **Interface Advantage**:

#### 13. **Difference Between Function and BiFunction in Java**
   - **Question**: What is the difference between `Function` and `BiFunction` in Java? Provide an example using `andThen` with `Function`.
   - **Answer**:
     - **Overview**:
       - Both are **functional interfaces** (single abstract method) introduced in Java 8 for functional programming.
       - Enable passing code as data (e.g., via lambda expressions).
     - **Function**:
       - Interface: `java.util.function.Function<T, R>`.
       - Method: `R apply(T t)`.
       - Takes one input (`T`), returns one output (`R`).
     - **BiFunction**:
       - Interface: `java.util.function.BiFunction<T, U, R>`.
       - Method: `R apply(T t, U u)`.
       - Takes two inputs (`T`, `U`), returns one output (`R`).
     - **Default Methods**:
       - `Function` has `andThen` and `compose` for chaining operations.
       - `BiFunction` has `andThen` for chaining a `Function` after the `BiFunction`.
     - **Example**:
       - **BiFunction**: Lambda `(x, y) -> x * y` multiplies two integers (e.g., `2 * 3 = 6`).
       - **Function**: Lambda `x -> 2 * x` doubles an integer (e.g., `6 * 2 = 12`).
       - **Chaining with `andThen`**:
         - Create `BiFunction a = (x, y) -> x * y`.
         - Create `Function b = x -> 2 * x`.
         - Chain: `a.andThen(b).apply(2, 3)`:
           - `a.apply(2, 3)` yields `6`.
           - `b.apply(6)` yields `12`.
         - Output: `12`.

#### 14. **Method Overriding vs. Method Hiding in Java**
   - **Question**: What is the difference between method overriding and method hiding in Java? When would you use method hiding instead of overriding?
   - **Answer**:
     - **Common Context**: Both involve inheritance (base class to child class).
     - **Method Overriding**:
       - Occurs when a child class provides a different implementation for a non-static method inherited from the base class.
       - Uses `@Override` annotation.
       - Example: A `Car` class has `drive()`. A `PetrolCar` subclass overrides `drive()` with a specialized implementation.
       - Behavior: At runtime, the child class’s method is called (runtime polymorphism).
     - **Method Hiding**:
       - Occurs when a child class redefines a **static** method from the base class.
       - Does not use `@Override` (as it’s not true overriding).
       - Example: A `Car` class has a static `drive()`. A `PetrolCar` subclass defines its own static `drive()`, hiding the parent’s version.
       - Behavior: The method called depends on the reference type, not the object type (compile-time binding).
     - **When to Use Method Hiding**:
       - Use when a static method in the base class needs a different implementation in the child class, typically for utility or class-specific static behavior.
     - **@Override Annotation**:
       - Compile-time annotation, ensuring the method is correctly overridden.
       - Krishna initially thought it persists at runtime but corrected that it’s discarded after compilation due to its **source retention policy**.
       - **Retention Policy Clarification**:
         - Annotations have three retention policies: `SOURCE`, `CLASS`, `RUNTIME`.
         - `@Override` uses `SOURCE`, so it’s discarded after compilation.
         - Runtime annotations (e.g., `@Autowired`) use `RUNTIME` retention.

#### 15. **What Are Memory Leaks in Java, and How to Prevent Them?**
   - **Question**: What is a memory leak in Java, and how do you protect your code from memory leaks?
   - **Answer**:
     - **Memory Leak Definition**:
       - Occurs when memory is allocated to objects/resources but not released, even after they’re no longer needed.
       - These objects remain in memory across garbage collection cycles, reducing available memory and degrading performance.
       - Common in long-running applications (e.g., servers, daemons) where leaks persist indefinitely.
     - **Prevention Practices**:
       1. **Close Resources**:
          - Explicitly close database connections, file streams, or other resources when done.
       2. **Use Try-with-Resources**:
          - Automatically closes resources implementing `AutoCloseable` (e.g., `Connection`, `FileInputStream`) when the try block exits.
          - Example: `try (Connection conn = getConnection()) { ... }` ensures `conn.close()` is called.
       - **Mechanism of Try-with-Resources**:
          - Works only with classes implementing `AutoCloseable` (has `close()` method).
          - Ensures resources are closed even if an exception occurs.
     - **Impact**:
       - Prevents memory leaks by deallocating unused resources, improving performance in production systems.

#### 16. **What Are Threads in Java, and How Do They Communicate?**
   - **Question**: What are threads in Java, and how do multiple threads communicate with each other?
   - **Answer**:
     - **Threads Definition**:
       - Threads are lightweight processes within a Java process, enabling concurrent execution.
       - A single-threaded program uses the main thread. Multithreaded programs use multiple threads for parallel tasks.
     - **Thread Communication**:
       - Needed when multiple threads access shared resources or code blocks to avoid conflicts.
       - **Mechanism**: Uses **locks** to synchronize access.
         - A thread locks a resource, preventing others from accessing it until released.
         - Communication occurs via methods:
           - `wait()`: Releases the lock and suspends the thread until notified.
           - `notify()`: Wakes one waiting thread.
           - `notifyAll()`: Wakes all waiting threads.
       - **Example Scenario**:
         - Four threads access a shared resource. One thread locks it, and others wait. The locking thread uses `notify()` or `notifyAll()` to signal when the resource is free.

#### 17. **What Is Serialization in Java, and Why Is It Needed?**
   - **Question**: What is serialization in Java, and why do we need it?
   - **Answer**:
     - **Serialization Definition**:
       - The process of converting an object into a byte stream for storage or transmission.
       - Classes implement the `Serializable` marker interface (no methods) to enable serialization.
     - **Purpose**:
       - Allows objects to be packaged securely for transport (e.g., over a network).
       - Ensures data integrity during transfer, preventing tampering by attackers.
       - **Deserialization**: Converts the byte stream back into an object at the destination.
     - **Use Case**:
       - Sending objects between client and server or saving object state to a file.

#### 18. **Why Do Frameworks Like Spring Recommend Coding to Interfaces?**
   - **Question**: Why do frameworks like Spring recommend coding to interfaces rather than classes? What benefits do interfaces provide in Spring?
   - **Answer**:
     - **Reasons**:
       1. **Dependency Inversion Principle (SOLID)**:
          - High-level modules should depend on abstractions (interfaces), not concrete implementations (classes).
          - Using interface references (e.g., `List` instead of `ArrayList`) decouples code, allowing flexible implementation changes.
       2. **Spring Autowiring**:
          - Interfaces enable dynamic dependency injection. Example: An `AuthenticationManager` can switch between different `PasswordHasher` implementations (e.g., SHA-256 vs. bcrypt) without changing the code, as Spring injects the appropriate bean.
       3. **Flexibility and Maintainability**:
          - Interfaces reduce code changes when implementations evolve, promoting loose coupling.
     - **Example**:
       - In the `AuthenticationManager` example, using a `PasswordHasher` interface allows swapping hashing algorithms via Spring’s dependency injection.

#### 19. **Difference Between Dependency Inversion Principle and Dependency Injection**
   - **Question**: What is the difference between the Dependency Inversion Principle (DIP) and Dependency Injection (DI)? Are they the same?
   - **Answer**:
     - **Related but Distinct**:
       - **Dependency Inversion Principle (DIP)**:
         - A SOLID principle stating that high-level modules should not depend on low-level modules; both should depend on abstractions (e.g., interfaces).
         - Promotes loose coupling by using interfaces to decouple modules.
         - Example: A service class uses an interface (`Repository`) rather than a concrete class (`SqlRepository`).
       - **Dependency Injection (DI)**:
         - A design pattern (used by Spring’s IoC container) where dependencies (beans) are injected into objects at runtime.
         - Implemented via `@Autowired` on fields, setters, or constructors.
         - Example: Spring injects a `Repository` bean into a service class.
     - **Key Difference**:
       - DIP is a design principle focused on abstractions and decoupling.
       - DI is a technique to achieve DIP by providing dependencies externally.
     - **Coupling**:
       - Coupling is how closely code components are linked. Tight coupling (direct class dependencies) makes changes harder; loose coupling (via interfaces) improves flexibility.
       - Spring’s DI reduces coupling by managing object creation and injection, freeing developers from manual dependency management.

The provider’s `authenticate` method (in `AbstractUserDetailsAuthenticationProvider`) calls `retrieveUser`, which uses a `UserDetailsService` (e.g., in-memory, JDBC, or custom) to load the user by username. The user’s credentials are validated, and the authenticated object is stored in the `SecurityContextHolder` for future requests.
